## 1. Overview

This plan breaks the requirements in [SRS-DOCS-I18N-001](multilingual-docs-srs.md) into work items, orders them as a sequence of pull requests, and defines how to verify each step. Requirement IDs such as FR-DIR-1 refer to the spec.

The work has three kinds of output:

1. **Repository changes** in this repository: the restructure, tooling scripts, CI workflows, and Crowdin configuration.
2. **External changes** in `grafana/website`, `grafana/docs-base`, and `grafana/writers-toolkit`, marked **[EXT]** in the spec.
3. **Translated content**: roughly 14,700 Markdown files produced through Crowdin.

The critical path runs through the external website changes and the translation volume, not through the repository changes. Repository work can finish in about six weeks. Translated content for all 19 languages takes considerably longer and is launched language by language.

## 5. Spikes

Two short spikes remove the largest technical unknowns. Both run in week 1, before any pull request that depends on them.

### S-1: Hugo multilingual behavior in docs-base

Goal: confirm the Hugo features the spec relies on in the Hugo version shipped in `grafana/docs-base`.

Steps:

1. Build a throwaway Hugo site with docs-base's Hugo version, two languages (`en-us`, `de-de`), and content provided through module mounts with `lang` (FR-CFG-3).
1. Confirm that `.Translations` links pages by path (FR-HUGO-1).
1. Confirm how `aliases` behave for a non-default language. Record whether Hugo prefixes absolute aliases with the language, and whether relative aliases resolve against the language root (FR-LINK-4).
1. Confirm `enableMissingTranslationPlaceholders` output for missing `i18n` keys (FR-I18N-3).
1. Confirm Hugo's generated heading IDs for non-ASCII headings, and that an explicit `{#id}` overrides them (FR-CONT-5).
1. Measure build time for 773 pages × 2 languages to extrapolate NFR-PERF-1.

Output: a short report and the minimum Hugo version for D-7.

### S-2: Crowdin Markdown round trip

Goal: confirm that Crowdin's Markdown parser preserves shortcodes, front matter, and code.

Steps:

1. Upload 10 representative English pages to a Crowdin sandbox project. Include pages with `refs` front matter, `docs/shared`, `admonition`, `figure` captions, `collapse`, raw HTML, tables, and fenced code.
1. Configure the parser per FR-TM-2 and pre-translate with machine translation.
1. Download and diff against English with the prototype verifier from T-2.

Output: a working Crowdin parser configuration, and a list of shortcode or front matter constructs that Crowdin mangles, each with a mitigation (placeholder regex, pre-processing, or post-processing in T-5).

## 6. Tooling design

All repository tooling is TypeScript under `scripts/docs/i18n/`, run with `tsx` like the existing `scripts/docs/generate-transformations.ts`. Shared code lives in one library so every tool parses Markdown the same way.

### Dependencies

`unified`, `remark-parse`, and `mdast-util-from-markdown` are already in `yarn.lock` as transitive dependencies. Add them as explicit root `devDependencies`, together with `remark-frontmatter`, and use the existing `js-yaml` for front matter. Hugo shortcodes aren't Markdown syntax, so the library tokenizes them separately with a small parser for `{{< name params >}}` and `{{% name params %}}`.

### Components

| ID  | Tool                         | Responsibility                                                                                                                                                                                                                                                         | Requirements                              |
| --- | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| T-0 | `lib/` (shared library)      | Read the locale list from `packages/grafana-i18n/src/languages.ts`; parse a page into front matter, shortcodes, code blocks, headings, links, and HTML elements; compute Git blob SHAs; map a file path to a URL for any language.                                     | Used by all tools                         |
| T-1 | `generate-hugo-languages.ts` | Write `docs/hugo/config/_default/languages.toml` and `module.toml` from the locale list. `--check` mode fails if the committed files differ.                                                                                                                           | FR-CFG-1, FR-CFG-2, FR-CFG-3, NFR-MAINT-2 |
| T-2 | `verify.ts`                  | Compare each target file against its English counterpart and report every violation listed in FR-VAL-1 and NFR-SEC-1, with file, line, and rule ID. Exit non-zero on any violation. `--locale` and `--changed-only` flags keep pull request runs fast.                 | FR-VAL-1, NFR-SEC-1, AC-2, AC-12          |
| T-3 | `sync.ts`                    | Detect added, moved, and deleted English files from `git diff --find-renames` against the merge base, and apply the same operation to every language tree. For added files, write a `source-copy` counterpart. Idempotent.                                             | FR-SYNC-3, FR-SYNC-4, AC-10               |
| T-4 | `anchors.ts`                 | For each translated heading, compute the English heading's ID with Hugo's GitHub-style algorithm (verified in S-1), and append `{#id}` when the translated text would produce a different ID. Runs on every Crowdin import.                                            | FR-CONT-5                                 |
| T-5 | `import.ts`                  | Post-process files downloaded from Crowdin: restore non-translatable front matter from English, write the `translation` block (FR-SYNC-1), run T-4, run Prettier, then T-2 on the result.                                                                              | FR-CONT-1, FR-SYNC-1, FR-TM-3             |
| T-6 | `status.ts`                  | Compute `translation.status` per file and write `docs/i18n/status.json` with per-locale counts and word counts. `--check` mode fails if statuses are out of date.                                                                                                      | FR-SYNC-2, FR-SYNC-6, AC-9                |
| T-7 | `glossary.ts`                | Build `docs/i18n/glossary/<locale>.tbx` from key pairs in `public/locales/en-US/grafana.json` and `public/locales/<locale>/grafana.json`, filtered to short UI labels (buttons, menu items, field names) and a hand-maintained do-not-translate list of product names. | FR-TM-5, FR-CONT-6, FR-CONT-8             |

Unit tests for T-0 to T-7 use Jest with small fixture trees under `scripts/docs/i18n/__fixtures__/`, following the repository's existing Jest setup.

### Front matter written by the tools

```yaml
translation:
  source_path: alerting/fundamentals/_index.md
  source_revision: 3f1c9e0b8a... # git hash-object of the English file
  method: machine-post-edited
  status: current
```

Hugo ignores unknown front matter keys, so this block needs no website change except for FR-SYNC-5's notice, which reads `.Params.translation`.

### Phase 4: Initial translation (weeks 6 onward, per language)

This phase is content work in Crowdin, not code. The download workflow from PR-7 delivers it as ordinary pull requests.

1. Post-edit in priority order: `introduction`, `fundamentals`, `setup-grafana`, then `tutorials`, `visualizations`, `alerting`, `datasources`, then everything else. Import marks post-edited pages `method: machine-post-edited`.
1. Human-translate the three sections required by NFR-QUAL-1.
1. Reviewers approve each locale's download pull request. The verifier blocks structurally broken files before a human sees them.

## 9. Repository size impact

Measured on the baseline: the English Markdown is 7.3 MB, and 1.6 MB when compressed with gzip. Nineteen translated trees add about 140 MB to the working tree. Git compresses text well, so pack growth is estimated at 30 to 60 MB; scripts in CJK languages compress less well, which is why the range is wide. PR-5 must measure the actual pack size growth on a fork before merge (NFR-SIZE-1).

`docs/README.md` gets sparse-checkout instructions (NFR-SIZE-2):

```bash
git sparse-checkout set --no-cone '/*' '!/docs/sources/*' '/docs/sources/en-US/' '/docs/sources/developers/'
```

## 10. Testing strategy

Testing happens at four levels.

| Level       | What                                                                                                                                                                                          | Where                                                         |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| Unit        | Every rule in T-2, move and delete handling in T-3, anchor computation in T-4 (including CJK and accented headings), blob SHA and status in T-6                                               | Jest, fixture trees in `scripts/docs/i18n/__fixtures__/`      |
| Integration | Crowdin round trip on the 10-page sample from S-2                                                                                                                                             | Crowdin sandbox, run before PR-7 merges and on parser changes |
| Build       | Hugo build of English plus one test language with no missing placeholders and no broken refs (FR-VAL-3)                                                                                       | `lint-build-docs.yml`                                         |
| End to end  | URL crawl for English (AC-5); language switcher, `hreflang`, shared-content fallback, link resolution (AC-6 to AC-8); alias redirects per language with the updated `test-aliases.py` (AC-10) | Deploy preview                                                |

The acceptance criteria in section 6 of the spec map to these tests as follows: AC-1 and AC-2 run in CI through T-2; AC-3 is a `status.json` query at launch; AC-4 is the build job; AC-5 to AC-8 and AC-10 are end-to-end checks on the preview; AC-9 and AC-11 are T-6 and T-1 unit tests; AC-12 is a T-2 unit test.

## 11. Risks

| Risk                                                                     | Likelihood       | Impact | Mitigation                                                                                                                    |
| ------------------------------------------------------------------------ | ---------------- | ------ | ----------------------------------------------------------------------------------------------------------------------------- |
